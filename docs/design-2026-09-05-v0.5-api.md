## Q1. Names — `rank_designs` / `DesignRanking`

**Recommendation: keep both, as sketched.**

The unit of the output is a *design*: a treated set **paired with a
duration**. `rank_markets` would name only half of the key and would then be
wrong the moment a second duration is passed — which is the normal case.
`CLAUDE.md` already frames the package goal as ranking "candidate treated
sets × experiment durations"; the name should match the frame.

`DesignRanking` for the result object, holding a polars frame plus the
per-cell `PowerResults`.

## Q2. Candidate identity — sorted, `", "`-joined string key

**Recommendation: canonical key = member units sorted by `str(unit)`, joined
with `", "`.**

This is exactly the oracle's convention (verified: all 30 rows of
`BestMarkets$location` are alphabetically sorted and `", "`-joined), so
parity joins are a straight string match with no translation layer.

The subtlety the handoff flagged is real: `PowerParams.treated` is typed
`tuple[Any, ...]`, so units are not guaranteed orderable (integer FIPS codes,
tuples, enums). Sorting by `str(unit)` gives a total order for **any** unit
type and reduces to alphabetical for the `str` units the fixture uses.

The frame therefore carries `candidate` (the canonical string) and
`n_units`. The original objects are not lost: `DesignRanking.candidates`
maps key → the original set, and `res.power(candidate, duration)` accepts
either the key string or the original set.

```python
def _candidate_key(units: Iterable[Any]) -> str:
    return ", ".join(sorted(str(u) for u in units))
```

Duplicate keys from distinct inputs (e.g. `1` and `"1"`) raise `ValueError`
at call time rather than silently colliding in the frame.

## Q3. Ranking columns and criterion

**Recommendation: rank on what geoexp can defend, not on what GeoLift
happens to print.**

The oracle's own composite (`rank`, driven by `abs_lift_in_zero` and
`Average_MDE`) is not reproducible under the clean-room rule — see the
characterization §5. Copying its *column names* while computing something
different would be worse than choosing our own.

`res.ranking` columns:

| Column | Source |
|---|---|
| `candidate`, `duration`, `n_units` | the candidate set |
| `mde` | interpolated, see Q4 |
| `mde_grid` | `PowerResults.mde()` — the grid point, unmodified |
| `power_at_target` | `power_curve()` at `target_effect_size` |
| `empirical_size` | `power_curve()` at `effect_size == 0` |
| `rmspe_pre` | mean of `simulations.rmspe_pre` over windows |
| `null_bias` | mean recovered lift at `effect_size == 0` (added 2026-09-08) |
| `h1_calibration_error` | recovery gap at `mde_grid`, multiplicative only (added 2026-09-08) |
| `proportion_total_y`, `holdout` | derived from the panel |
| `investment` | `cpic × target_effect_size × Σ Y_treated`, see Q7 |
| `rank` | competition rank over the ordering below |

**Default ordering**: `mde` ascending, then `empirical_size` ascending, then
`rmspe_pre` ascending, then `candidate` lexicographic.

The reasoning behind that sequence: MDE is the answer to the question the
package exists to ask; empirical size is the guard against a design that
"detects" because it over-rejects; `rmspe_pre` is the guard against a design
whose pre-period fit was poor to begin with; the lexicographic key makes the
order fully deterministic so two runs never disagree on ties.

**One documented caveat.** `empirical_size` is a rate over the lookback
window. At `lookback_window = 1` there is exactly one test, so it is 0 or 1
on both sides — a coin flip, not a false-positive rate (measured: 27 of 30
candidates at 0, 3 at 1). `rank_designs` emits a warning when
`lookback_window < 10` and `empirical_size` participates in the ordering.

**A second caveat, and the more important one.** Rank order by `mde` is *not*
a stable cross-implementation quantity. Measured on the fixture: geoexp and
GeoLift agree on 226 of 240 power cells (mean absolute difference 0.0063), yet
their MDE orderings agree only at Kendall τ = 0.40. Refining the effect grid
from 6 to 21 points does not move that (0.398 → 0.414). Collapsing a power
curve into one scalar amplifies boundary noise: near the crossing point, one
extra rejection out of ten lookback windows shifts the interpolated MDE
enough to reorder neighbours that were never meaningfully different.

`mde` stays the primary sort key — it is the quantity a user is asking for,
and within one implementation it is deterministic and reproducible. But two
things follow. First, `docs/methodology.md` must say plainly that small rank
differences near ties are not meaningful, and point readers at
`power_at_target` and the full curve, which are stable. Second, and binding on
Q6: **no test may assert on ranking agreement** — not against GeoLift, not
against any other package. See
`docs/geolift-oracle-characterization.md` §9 for the experiment that
established this.

## Q4. MDE — interpolated in geoexp, grid value kept alongside

**Recommendation: interpolate, and expose the grid value too.**

Three reasons, in order of weight:

1. **Grid MDE makes the ranking degenerate.** `mde()` returns grid points,
   so on the default 6-point grid dozens of candidates tie on the primary
   sort key. A ranking whose primary key has six distinct values is not a
   ranking. This is the tie-break problem the handoff anticipated, and
   interpolation dissolves it rather than papering over it.
2. **The oracle is off-grid too.** None of its 30 `Average_MDE` values lands
   on the supplied grid. Interpolating moves geoexp closer to the oracle in
   spirit — though *not* to numerical agreement, which we do not claim.
3. **It needs nothing private.** `power_curve()` gives `(effect_size,
   power)`; the interpolation is ours, in our layer, from public output.

Method: restrict to the sign of the grid, enforce monotonicity by running
maximum (power curves from finite simulation are noisy), then linear
interpolation to the first crossing of `target_power`. Returns `null` when
the curve never crosses — never an extrapolated number.

`mde_grid` carries `PowerResults.mde()` unchanged, so the strict upstream
answer is always one column away, and the difference between the two is
inspectable rather than buried.

`docs/methodology.md` must state that `geoexp.mde` is a geoexp construct and
is **not** the oracle's `Average_MDE`.

## Q5. Signature

**Recommendation: forward the power contract verbatim; own only what fans
out.**

```python
def rank_designs(
    panel: pl.DataFrame,
    *,
    estimator: PowerEstimator,
    unit: str,
    time: str,
    outcome: str,
    candidates: Sequence[Iterable[Any]],  # geoexp: explicit sets (0.1.0)
    durations: int | Sequence[int],  # geoexp: fans out
    rng: np.random.Generator,  # geoexp: MANDATORY
    target_power: float = 0.8,  # geoexp: ranking criterion
    target_effect_size: float = 0.10,  # geoexp: ranking criterion
    cpic: float | None = None,  # geoexp: see Q7
    n_jobs: int = 1,  # geoexp: candidate-level
    # --- forwarded verbatim to simulate_power ---
    effect_sizes: Sequence[float] = DEFAULT_EFFECT_SIZES,
    effect_type: EffectType = "multiplicative",
    lookback_window: int = 1,
    alpha: float = 0.1,
    permutation_type: PermutationType = "block",
    block_size: int | None = None,
    side: Side = "two-sided",
    ns: int = 1000,
    on_error: Literal["raise", "record"] = "raise",
) -> DesignRanking: ...
```

- **`effect_sizes` stays a grid.** MDE needs a curve; a single target effect
  cannot produce one. `target_effect_size` is the separate scalar that feeds
  `power_at_target`, and it need not be a grid member.
- **`rng` is mandatory**, positionally keyword-only, no default. Inheriting
  augsynth-py's strict posture is the stated intent, and it is also forced:
  `permutation_type="iid"` — the oracle's default — requires an `rng`
  upstream. Per contract, one child generator per candidate via
  `rng.spawn(len(candidates))`, so the result is order-independent under
  candidate-level parallelism and restartable.
- **`n_jobs` parallelizes across candidates**, and `n_jobs=1` is passed down
  to every `simulate_power` call — joblib does not nest workers.
- **`on_error="record"`** is forwarded so a long sweep survives per-cell
  failures; affected cells surface as `null` ranking metrics, never as
  silently dropped rows.

**Typing gap to resolve.** `EffectType` is exported from `augsynth_py`, but
`PermutationType` and `Side` are **not** in `augsynth_py.__all__` — they live
in `augsynth_py.inference`. Under the consumption rule geoexp should not
reach into a submodule for them. For 0.1.0, declare geoexp-local `Literal`
aliases mirroring upstream, with a comment pointing at the upstream
definition; and **file a proposal against augsynth-py to export both**. When
that lands, the local aliases become re-exports. This is the consumption
rule working as designed: an API gap becomes an upstream proposal.

## Q6. Parity surface

**Recommendation: assert on the shared substrate; exclude, in writing, what
the clean-room rule puts out of reach.**

The parity test feeds GeoLift's own candidates back to geoexp as explicit
candidate sets (split the `location` key on `", "`), so both sides score the
*same* designs — enumeration is out of scope for 0.1.0 anyway.

**Read the candidates from `PowerCurves`, not `BestMarkets`.** `BestMarkets`
is filtered by GeoLift's own selection step: on the 40-market single-candidate
run it returned 39 rows while `PowerCurves` carried all 40 (`san francisco`
was computed and then dropped). Joining on `BestMarkets` silently loses
candidates and makes the test's coverage depend on the oracle's ranking
choices.

**Target the power curve, and run it wide.** The measured agreement is 226 of
240 cells exact across 40 candidates × 6 effect sizes at
`lookback_window = 10` (characterization §7.2). A sweep of that shape gives
240 assertions instead of 6, and is what would actually catch a regression in
panel handling, placebo construction, effect injection or the conformal
p-value. Set `lookback_window` well above 1: at 1 the power is a single 0/1
outcome per cell and the test loses nearly all of its resolution.

**In parity:**

| Quantity | Tolerance |
|---|---|
| `power` per (candidate, duration, effect_size) | `atol=1e-6, rtol=1e-5` on cells away from the boundary; see below |
| `att` vs `AvgATT` | `rtol=1e-5`, **`atol=1e-3`** |
| `investment` vs `Investment` | `atol=1e-6, rtol=1e-5` |

The `att` tolerance is the one relaxation, and it is justified rather than
convenient: measured agreement is ~2e-4 absolute on values of order 1e2–1e3,
i.e. ~1e-6 *relative*. The default `atol=1e-6` is simply the wrong scale for
an unnormalized outcome. The relative tolerance is untouched.

`power` needs one honest qualification. 226 of 240 cells match exactly, but
14 do not, by up to 0.2 — all of them at low effect sizes where the curve
crosses the decision threshold and a single rejection out of ten windows
moves the value by 0.1. This is not implementation drift; it is the
discreteness of a rate over ten placebo tests, and it will not vanish with a
tighter tolerance. The test should assert exact equality where both sides are
saturated (measured: every cell at effect size ≥ 0.15) and allow one
lookback-window step (`atol = 1/lookback_window`) elsewhere, rather than
blanket-relaxing every cell to hide fourteen.

**Explicitly out of parity**, with the reason recorded in the test file so
nobody re-litigates it later: `Average_MDE` (off-grid, definition not in
published material), `abs_lift_in_zero` (definition not established),
`rank` (composite not established, and inherits the above),
`AvgScaledL2Imbalance` (a different metric from `rmspe_pre` — 0.4462 vs
0.0334 for the same candidate), `AvgDetectedLift` (affinely related to
`att_pct`, constant ratio 1.02125 on the probed candidate — different
denominators, so not an equality assertion).

Both sides must pin `conformal_type`/`permutation_type` and the effect grid
explicitly: their defaults differ, and GeoLift's own help page contradicts
itself about the effect-size default.

## Q7. cpic / budget — take `cpic` in 0.1.0, defer `budget`

**Recommendation: ship the `investment` column now.** *(Enumeration was also
pulled into 0.1.0 on 2026-09-08 — see the status note at the top. It is a
separate function, `enumerate_candidates`, so `rank_designs`'s signature is
unchanged.)*

This inverts the handoff's "stretch only if trivial" — it turned out to be
*more* than trivial, it is the safest thing in the release. Measured
exactly: `Investment = cpic × effect_size × Σ Y_treated` over the treatment
window, verified to the cent (108465 × 0.05 = 5423.25; × 0.25 = 27116.25).
It is a function of the panel and the grid alone, touches no estimator
internals, and is **exactly parity-testable** — which is more than the MDE
column can say.

`cpic=None` (default) omits the column entirely; no fabricated costs.

**`budget` is deferred to 0.2.x**, unchanged. Budget acts as a *filter* over
candidates, which is enumeration — the thing 0.1.0 explicitly does not do.

## 8. Validation-rule tension — resolved 2026-09-08

`CLAUDE.md` states, as non-negotiable:

> Every public ranking/selection feature must have at least one test in
> `tests/validation_against_r/` that runs the same input through this package
> and through R `GeoLiftMarketSelection` via rpy2, asserting numerical
> agreement within a documented tolerance.

Under this design, `mde` and `rank` are public ranking features that
**cannot** satisfy that rule: their oracle counterparts are not reproducible
without reading GeoLift's source, which the clean-room rule forbids. The two
rules are in direct conflict for those columns, and only the maintainer can
resolve it.

Two routes out were tested and closed, so the choice below is not a matter of
taste:

- *Match the oracle's columns.* Impossible without reading GeoLift's source.
  And now known to be pointless as well: rank order by MDE is unstable by
  construction, so even an exact copy of their formula would be chasing a
  number that a correct reimplementation cannot be expected to reproduce.
- *Validate them against a second package instead.* Tried, with
  `MarketMatching` — a genuine method-independent benchmark. Rank concordance
  came out at τ ≈ 0.35, too weak to assert on, and the weakness survived every
  attempt to explain it away (finer grid, filtering bad candidates). Recorded
  in full in `docs/geolift-oracle-characterization.md` §9.

The residue is that `mde` and `rank` cannot be externally validated by any
route available to us — and, per §7.2 of the characterization, this reflects
the fragility of a derived scalar rather than any defect in geoexp. The
substrate they are derived *from* validates strongly: 226 of 240 power cells
exact.

Options:

- **(a) Narrow the rule to the shared substrate.** Parity is required on
  every quantity geoexp and the oracle both compute (power, ATT,
  investment); geoexp-specific ranking columns are covered by unit tests
  plus a methodology entry stating what they are and what they are not.
- **(b) Drop the non-parity-testable columns.** Honest, but removes MDE-based
  ranking — the package's reason to exist.
- **(c) Match GeoLift exactly.** Requires reading its source. Forbidden.

**Resolved: (a).** Approved by the maintainer on 2026-09-08 and applied —
`CLAUDE.md`'s validation rule now reads as proposed below. The remaining
recommendations in this document (Q1–Q7) are still awaiting sign-off.

The amendment, as applied, has `CLAUDE.md` read: *"Every public
feature that has a `GeoLiftMarketSelection` counterpart must have a parity
test… Features with no reproducible counterpart must be listed in
`docs/geolift-oracle-characterization.md` §6 with the reason, and covered by
unit tests plus a `docs/methodology.md` entry."*

That keeps the rule's teeth — nothing escapes by being merely inconvenient,
only by being genuinely unreachable, and each escape is named in writing.

It also loses less than it first appears. The rule's purpose is to catch a
geoexp bug before it ships. A 240-cell power sweep does that better than a
ranking assertion ever could: every ranking column is a pure function of the
power curve plus panel arithmetic, so an error upstream of the ranking shows
up in the sweep, and an error in the ranking itself is deterministic and fully
covered by unit tests. The columns leaving the parity surface are the ones
where an assertion would have been theatre.
